## 요약 판단

직전 리뷰의 P1 세 항목은 구현 에이전트가 실제로 수정했다. `SelectChoice()` valid key 검증, `PlayCatalog()` 재호출 시 이전 카탈로그 종료 이벤트, Motion offset 분리는 모두 코드에 반영되어 있다. 그러나 수정 방식이 완전히 닫힌 것은 아니다. `PlayCatalog()`는 새 catalog 유효성 검증 전에 기존 catalog를 종료하므로 실패한 재생 요청이 현재 대화를 끊는다. Motion은 offset 분리 방향은 맞지만 취소된 이전 task의 `finally`가 새 Motion의 offset을 지울 수 있는 ABA 문제가 남아 있다.

## 구조 평가

HDialogue의 큰 구조는 여전히 적절하다. 그래프 실행, 텍스트 출력, 태그 파싱, 포트레이트, 오디오 어댑터, 에디터 검증기가 분리되어 있다. 최근 수정으로 런타임 계약도 일부 단단해졌다.

하지만 구조적 부채는 남아 있다.

- `DialogueDirector`는 여전히 모든 node processor를 직접 가진다.
- `FacingDirection`이 slot과 facing 두 의미를 동시에 담당한다.
- parser/validator의 커스텀 태그 정의가 분리되어 있다.
- 포트레이트 active/inactive 정책이 controller와 stage director 사이에서 완전히 정리되지 않았다.

이 상태는 프로토타입 후반 또는 알파 단계로 보는 것이 맞다. 기능은 있으나 계약이 완전히 닫힌 상태는 아니다.

## 장점

- `SelectChoice()`가 `validChoiceKeys`를 검증한다. 조건 미통과 선택지 우회 문제는 큰 폭으로 줄었다.
- `PlayCatalog()` 재호출 시 이전 catalog에 `OnCatalogExit("Replaced")`를 발행한다. 기존 "조용한 취소" 문제는 개선됐다.
- `motionOffset` 분리는 방향이 맞다. slot base, pose offset, motion offset을 더 이상 같은 값으로 덮어쓰지 않는다.
- `AudioManagerBlipAdapter`의 null guard는 유지되고 있다.
- `DialogueTextController` Event 토큰은 Instant 모드에서도 발화된다.
- `CharacterStageDirector._GetOrCreateController()`는 기존 컨트롤러에 `Bind()`를 반복하지 않는다.

## 치명적 결함

### P1. `PlayCatalog()` 실패 요청이 현재 대화를 먼저 종료한다

파일: `HDialogue/Runtime/Graph/DialogueDirector.cs`  
관련 위치: `PlayCatalog()` 90-114

현재 `PlayCatalog(catalog, startNodeOverride)`는 catalog null만 검사한 뒤 곧바로 `_CancelCurrentCatalog("Replaced")`를 호출한다. 그 다음에 새 catalog의 start node를 계산한다. 이 순서는 틀렸다.

실패 시나리오:

1. 기존 대화가 진행 중이다.
2. 외부에서 잘못된 catalog 또는 root가 없는 catalog를 `PlayCatalog()`로 넘긴다.
3. 기존 대화는 `OnCatalogExit("Replaced")`와 함께 취소된다.
4. 새 catalog는 `startNode == null`로 시작 실패한다.
5. 결과적으로 아무 대화도 재생되지 않는다.

이건 "교체 성공"이 아니라 "새 요청 검증 실패로 기존 세션 손실"이다.

수정 방향:

- 새 catalog와 start node 유효성을 먼저 검증한다.
- 새 실행이 가능한 것이 확인된 뒤 기존 catalog를 취소한다.
- 즉 순서는 `validate new request → cancel current → create CTS → assign state → start`가 맞다.

### P1. Motion 취소 복구가 새 Motion을 지울 수 있다

파일: `HDialogue/Runtime/Portrait/CharacterPortraitController.cs`  
관련 위치: `_ShakeAsync()` 251, `_BounceAsync()` 269, `_Cleanup()` 336

`motionOffset` 분리 자체는 맞지만, `finally`에서 token 소유권 확인 없이 무조건 `motionOffset = Vector2.zero`와 `_ApplyAnchoredPosition()`을 실행한다.

위험 시나리오:

1. Shake 실행 중 Bounce 호출.
2. Bounce가 `_Cancel(Motion)`으로 Shake CTS를 취소하고 새 Motion CTS를 등록한다.
3. Bounce가 `motionOffset`을 갱신하기 시작한다.
4. 늦게 깨어난 Shake의 `finally`가 실행되어 `motionOffset = Vector2.zero`를 수행한다.
5. 새 Bounce motion이 한 프레임 이상 끊기거나 위치가 튄다.

기존 `_Cleanup(channel, token)`은 token 검증을 하지만, 검증 전에 이미 offset을 지운다. ABA 방지 의도가 핵심 상태에는 적용되지 않았다.

수정 방향:

- `finally`에서 먼저 현재 channel token이 자기 token인지 확인해야 한다.
- 예: `_IsCurrentToken(TransitionChannel.Motion, ct)` 헬퍼 추가 후 소유자일 때만 `motionOffset = Vector2.zero`.
- 또는 Motion별 local offset을 별도 구조로 두고, 적용 단계에서 현재 token만 반영한다.

## 주요 이슈

### `Stop()`과 `PlayCatalog()` 종료 key 정책이 아직 약하다

파일: `HDialogue/Runtime/Graph/DialogueDirector.cs`

`Stop()`은 빈 문자열, `PlayCatalog()` 교체는 `"Replaced"`를 사용한다. `"Replaced"`는 개선이지만 빈 문자열은 여전히 의미가 약하다. 외부 구독자가 빈 문자열을 정상 ExitKey 누락으로 볼지, 사용자 취소로 볼지, 강제 중단으로 볼지 알 수 없다.

권장:

- `DialogueExitReason` enum 또는 상수 키를 둔다.
- 정상 ExitNode의 `ExitKey`와 시스템 종료 사유를 구분한다.

### `validChoiceKeys`는 fallback 경로를 검증하지 않는다

파일: `HDialogue/Runtime/Graph/DialogueDirector.cs`  
관련 위치: `_ProcessChoiceNode()` 273-278

유효 선택지가 0개일 때 `FallbackChoiceKey`가 있으면 바로 반환한다. 이 key가 실제 port/edge에 있는지는 runtime에서 `_ResolveNextNode()`에 맡긴다. validator도 fallback key 검증을 하지 않는다.

권장:

- fallback key가 choice/entry/hub edge에 존재하는지 validator에서 검증한다.
- runtime에서도 fallback key가 outgoing hub edge에 없으면 더 명확한 error를 남긴다.

### Hide fade 완료 후 GameObject 비활성화 정책이 아직 정리되지 않았다

파일:

- `HDialogue/Runtime/Portrait/CharacterStageDirector.cs`
- `HDialogue/Runtime/Portrait/CharacterPortraitController.cs`

`HideCharacter()`는 Hide 직후 `!ctrl.IsVisible`일 때만 `SetActive(false)`를 한다. Fade hide는 비동기 완료 후 `IsVisible=false`가 되므로 GameObject는 계속 active로 남는다. 이 정책이 의도라면 주석을 고쳐야 하고, 풀링 비활성화가 의도라면 완료 후 비활성화 경로가 필요하다.

### 필수 SerializeField Assert가 아직 없다

파일:

- `HDialogue/Runtime/Controller/DialogueTextController.cs`
- `HDialogue/Runtime/Portrait/CharacterPortraitController.cs`
- `HDialogue/Runtime/Portrait/CharacterStageDirector.cs`

`tmpText`, `image`, `controllerPrefab` 같은 사실상 필수 연결이 null-safe로 조용히 통과한다. 프로젝트 규칙상 필수 연결은 Assert 대상이다. 아직 컨벤션 미준수다.

### `DialogueTextController`의 `Sfx` 토큰은 여전히 no-op이다

파일: `HDialogue/Runtime/Controller/DialogueTextController.cs`  
관련 위치: `DialogueTokenType.Sfx` 처리

parser는 `<sfx=...>`를 토큰으로 만들지만 controller는 처리하지 않는다. 스펙상 기능이면 미구현이고, 아직 의도적으로 보류라면 validator 또는 문서에서 명확히 경고해야 한다.

### 커스텀 태그 정의 중복은 그대로다

파일:

- `HDialogue/Runtime/Parser/DialogueTagParser.cs`
- `HDialogue/Editor/Validator/DialogueTextValidator.cs`

TMP 태그만 `DialogueTagParser.TmpTags`로 공용화됐다. `effectTags`, `pairTags`, `requiredArgTags`, `floatArgTags`, `allCustomTags`는 여전히 양쪽에 흩어져 있다. 태그가 추가되면 다시 어긋난다.

### `FacingDirection`이 slot과 facing 의미를 동시에 가진다

파일:

- `HDialogue/Runtime/Portrait/FacingDirection.cs`
- `HDialogue/Runtime/Portrait/SlotConfig.cs`
- `HDialogue/Runtime/Graph/Nodes/DialogueLineNode.cs`

`FacingDirection`은 캐릭터 방향이자 stage slot이다. 지금은 Left/Right 두 값뿐이라 편하지만 의미가 다르다. 이후 중앙 슬롯이나 3인 배치가 들어오면 확장성이 깨진다.

### `DialogueCatalogValidator` 검증 범위가 아직 좁다

파일: `HDialogue/Editor/Validator/DialogueCatalogValidator.cs`

아직 없는 검증:

- Choice fallback key 존재 여부
- Branch IntRange key 형식
- Branch IntRange overlap
- Branch Switch key 빈 값/중복
- branch 결과 key와 outgoing edge 일치
- speaker/pose/slot registry/layout 통합 검증

## 보안 및 안정성

- 선택지 조건 우회는 `validChoiceKeys`로 상당히 완화됐다.
- 다만 fallback key와 branch key는 여전히 validator/runtime 검증이 부족하다.
- async cancellation은 더 나아졌지만 Motion offset 처리에 token 소유권 검증이 빠져 있다.
- `UniTaskVoid`에서 `OperationCanceledException` 외 예외가 발생할 때 관측 정책이 명확하지 않다.
- 필수 참조 null을 조용히 허용하는 부분은 런타임 무음 실패를 만든다.

## 구조적 결함

- `DialogueDirector`가 여전히 node processor를 모두 직접 가진다.
- `FacingDirection`의 의미 중복은 타입 설계 결함이다.
- 태그 정의가 parser/editor validator로 흩어져 있다.
- 포트레이트 Hide 완료 정책이 StageDirector와 PortraitController 사이에 명확한 단일 책임으로 정리되지 않았다.
- asmdef 참조가 넓다. 실제 코드 기준 `HCUP.HUI`, `HCUP.HCore`, `HCUP.HUtil` 참조 필요성을 재검토해야 한다.
