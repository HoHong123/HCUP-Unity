## 요약 판단

HDialogue는 직전 리뷰 이후 핵심 지적 일부를 실제로 반영했다. `Stop()` 종료 이벤트, `OnChoicePresent`의 유효 선택지 전달, 포트레이트 슬롯 타입 안정화, AudioManager null guard 등은 개선이다. 하지만 아직 운영 가능한 대화 시스템으로 보기에는 이르다. 특히 선택지 입력 검증, PlayCatalog 재호출 종료 계약, Motion 취소 위치 복구, 필수 참조 Assert 정책, Parser/Validator 규칙 단일화가 남아 있다.

완성도는 현재 기준 68%다. 구조는 잡혔지만 런타임 계약과 에디터 검증이 아직 충분히 닫혀 있지 않다.

## 직전 리뷰 및 수정 보고 확인

- 수정/결과 보고: 별도 구현 에이전트 보고 파일은 발견되지 않았다. 직전 리뷰 상단의 "Claude Code 수정사항 반영 후 재검토" 섹션이 사실상 결과 보고 역할을 하고 있다.

## 구조 평가

전체 구조는 `Graph`, `Controller`, `Parser`, `Effect`, `Portrait`, `Audio`, `Editor`로 나뉘어 있고, 큰 경계는 적절하다. 그래프 데이터는 HWindows NodeWindow 기반 노드와 카탈로그가 담당하고, `DialogueDirector`가 런타임 실행을 조율한다. 텍스트 출력과 포트레이트 연출도 별도 컴포넌트로 분리되어 있다.

다만 `DialogueDirector`는 여전히 중심 책임이 과하다. 그래프 순회, 상태 전이, 라인 빌드, choice/branch/variable/wait/cinematic 처리, 텍스트 컨트롤러 대기, stage context 생성까지 모두 한 클래스에 있다. 지금은 버틸 수 있지만 localization, save/resume, history, auto mode, voice acting이 붙으면 확장 비용이 빠르게 증가한다.

포트레이트 쪽은 string slot에서 `FacingDirection` 기반 slot으로 바뀐 점은 타입 안정성 측면에서 좋다. 하지만 `FacingDirection`이 "캐릭터가 바라보는 방향"과 "화면 슬롯 위치" 양쪽 의미로 쓰인다. 지금은 Left/Right 두 슬롯이라 굴러가지만, 의미가 섞인 enum 재사용은 이후 중앙 슬롯, 후면 방향, 3인 이상 배치에서 바로 막힌다.

## 장점

- `DialogueDirector.OnChoicePresent`가 `Action<DialogueChoiceNode, IReadOnlyList<ChoiceData>>`로 바뀌어 UI가 유효 선택지 목록을 받을 수 있게 됐다.
- `DialogueDirector.Stop()`이 현재 카탈로그가 있고 Idle이 아닐 때 `OnCatalogExit(currentCatalog, "")`를 발행하도록 개선됐다.
- 포트레이트 `StageLayoutSO`와 `SlotConfig`가 string key 대신 `FacingDirection`을 쓰도록 바뀌어 typo 기반 슬롯 오류가 줄었다.
- `CharacterStageDirector._GetOrCreateController()`가 기존 컨트롤러에는 `Bind()`를 반복 호출하지 않도록 바뀌어 default pose 재초기화 위험이 줄었다.
- `AudioManagerBlipAdapter`가 `AudioManager.Instance == null`을 방어한다.
- `DialogueTextController`의 Event 토큰은 Instant 모드에서도 발화된다. 이 판단은 맞다. 이벤트는 시간 지연이 아니라 상태 변화다.
- TMP 태그 목록은 `DialogueTagParser.TmpTags`로 일부 단일화됐다.

## 치명적 결함

### P1. `SelectChoice()`가 현재 유효 선택지 key를 검증하지 않는다

파일: `HDialogue/Runtime/Graph/DialogueDirector.cs`  
관련 위치: `SelectChoice()` 123, `_ProcessChoiceNode()` 265

`_ProcessChoiceNode()`는 `validChoices`를 계산해 UI에 넘긴다. 하지만 `SelectChoice(string choiceKey)`는 `state == WaitingForChoice`만 확인하고 `choiceTcs.TrySetResult(choiceKey)`를 호출한다. 즉 UI나 외부 코드가 조건 미통과 key, fallback key, 임의 문자열을 넘겨도 director는 그대로 `_ResolveNextNode()`에 넘긴다.

결과:

- 조건식은 표시 단계에서만 의미가 있고, 선택 실행 단계에서는 보안/무결성 경계가 아니다.
- 외부 입력 실수나 UI 버그가 곧바로 잘못된 분기로 이어진다.
- hub edge가 없으면 Finished로 끝나지만, edge가 있으면 조건을 우회한다.

필수 수정:

- 현재 대기 중인 valid key 집합을 director 내부에 저장한다.
- `SelectChoice()`에서 `choiceKey`가 valid key에 포함되는지 검증한다.
- 검증 실패 시 warning 후 무시해야 한다. Finished 처리도 부적절하다.

### P1. `PlayCatalog()` 재호출은 이전 카탈로그를 종료 이벤트 없이 취소한다

파일: `HDialogue/Runtime/Graph/DialogueDirector.cs`  
관련 위치: `PlayCatalog()` 89, `_CancelAndDisposeCts()` 445

`Stop()`은 `OnCatalogExit`를 발행하도록 개선됐지만, `PlayCatalog()`는 시작 초입에서 `_CancelAndDisposeCts()`만 호출한다. 이미 대화가 진행 중인 상태에서 새 카탈로그를 재생하면 이전 카탈로그는 종료 이벤트 없이 취소된다.

문제:

- 외부 UI/입력 잠금/퀘스트 상태가 `OnCatalogExit`에 묶여 있으면 재생 교체 시 정리가 누락된다.
- `Stop()`과 `PlayCatalog()`의 취소 계약이 다르다.
- "새 대화 시작은 기존 대화 종료"라는 일반 기대와 맞지 않는다.

필수 수정:

- `PlayCatalog()` 초입에서 활성 카탈로그가 있으면 `Stop()`에 준하는 종료 처리 또는 별도 `CancelCurrentCatalog(exitKey)`를 호출한다.
- 종료 사유 key를 명확히 정의한다. 빈 문자열은 의미가 약하다. 예: `"Stopped"`, `"Replaced"`, `"Cancelled"`.

### P1. Motion 취소 시 포트레이트 위치 복구가 보장되지 않는다

파일: `HDialogue/Runtime/Portrait/CharacterPortraitController.cs`  
관련 위치: `Shake()` 144, `Bounce()` 150, `_ShakeAsync()` 245, `_BounceAsync()` 263

`Shake()`와 `Bounce()`는 같은 `TransitionChannel.Motion`을 사용하고 새 Motion 호출 시 기존 Motion을 취소한다. 그런데 `_ShakeAsync()`와 `_BounceAsync()`는 `OperationCanceledException` catch 후 `finally`에서 `_Cleanup()`만 하고 `anchoredPosition`을 origin으로 되돌리지 않는다. origin 복구는 정상 루프 종료 후에만 실행된다.

재현 가능한 위험:

- shake 중 bounce 호출
- `_ShakeAsync()` 취소
- shake가 남긴 offset 위치에서 bounce가 origin을 잡음
- motion이 누적 오차를 만든다

필수 수정:

- `_ShakeAsync()`/`_BounceAsync()`에서 `origin`을 try 밖 또는 nullable로 보관하고, finally에서 소유 token이 유효한 경우 복구한다.
- 더 좋은 구조는 base anchored position과 motion offset을 분리하는 것이다. `SetSlot`/`SetPose`와 Motion이 같은 `anchoredPosition`을 직접 쓰는 현재 방식은 충돌 가능성이 높다.

## 주요 이슈

### `DialogueTextController.PlayLine(null)` 방어가 없다

파일: `HDialogue/Runtime/Controller/DialogueTextController.cs`  
관련 위치: `PlayLine()` 83

`PlayLine(DialogueLine line)`은 `line.RawText`, `line.OverrideBlipToken`을 바로 읽는다. public API이므로 호출자가 null을 넘기면 NRE가 난다. `DialogueLine`이 현재 struct라 일반 호출에서는 null이 불가능하지만, API 설계상 null 방어 지적이 이전 리뷰에 남아 있었고, 실제로는 struct 선택 덕분에 해당 위험은 낮다. 다만 `RawText`는 null일 수 있고 parser가 null을 빈 배열로 처리한다.

정정 판단:

- "PlayLine(null)" 자체는 `DialogueLine`이 struct라 컴파일 레벨에서 대부분 차단된다.
- 더 현실적인 문제는 `tmpText` 필수 참조가 null이어도 조용히 진행된다는 점이다.

### 필수 SerializeField가 Assert로 강제되지 않는다

파일:

- `HDialogue/Runtime/Controller/DialogueTextController.cs`
- `HDialogue/Runtime/Portrait/CharacterPortraitController.cs`
- `HDialogue/Runtime/Portrait/CharacterStageDirector.cs`

`tmpText`, `image`, `controllerPrefab`, `registry`, `layout`은 실제 플로우상 대부분 필수다. 현재 코드는 null-safe로 조용히 통과하거나 warning만 남긴다. 사용자 컨벤션상 "반드시 true여야 하는 연결"은 early exit보다 Assert가 맞다.

권장:

- `Awake()` 또는 `OnValidate()`에서 `Debug.Assert` 또는 `UnityEngine.Assertions.Assert` 적용.
- 선택 참조와 필수 참조를 명확히 나눈다. 예: `stageDirector`는 선택 가능, `tmpText`는 필수.

### `Hide()` 페이드 완료 후 GameObject 비활성화 계약이 어긋난다

파일: `HDialogue/Runtime/Portrait/CharacterStageDirector.cs`, `CharacterPortraitController.cs`  
관련 위치: `HideCharacter()` 153, `_HideAsync()` 180

`HideCharacter()`는 `ctrl.Hide(transition)` 호출 직후 `if (!ctrl.IsVisible) ctrl.gameObject.SetActive(false)`를 수행한다. Fade transition에서는 `IsVisible`이 `_HideAsync()` 완료 후 false가 되므로 즉시 비활성화되지 않는다. `_HideAsync()`는 image만 disable하고 gameObject는 계속 active로 둔다.

문제:

- 주석은 "Fade 전환은 애니메이션 중이므로 비활성화 보류"라고 설명하지만, 완료 후 비활성화하는 후속 경로가 없다.
- 숨겨진 포트레이트 컨트롤러가 계속 active 상태로 남는다.
- 성능 문제는 작지만, 풀링 계약과 코드 주석이 다르다.

권장:

- `CharacterPortraitController.OnTransitionComplete`를 이용해 Hide 완료 시 비활성화한다.
- 또는 `Hide()`가 완료 후 직접 `gameObject.SetActive(false)`를 선택적으로 수행하도록 정책을 둔다.

### `DialogueTagParser`와 `DialogueTextValidator`의 커스텀 태그 정의가 아직 중복이다

파일:

- `HDialogue/Runtime/Parser/DialogueTagParser.cs`
- `HDialogue/Editor/Validator/DialogueTextValidator.cs`

TMP 태그 목록은 공용화됐지만, `effectTags`, `pairTags`, `requiredArgTags`, `floatArgTags`, `allCustomTags`는 여전히 분리되어 있다. validator 주석도 "태그 추가 시 양쪽 동시 갱신"이라고 명시한다. 이건 단일화가 아니다.

추가 문제:

- parser는 `</wave>`가 `<shake>`를 닫는 mismatch를 감지하지 않고 `openEffects.Pop()`만 한다.
- validator는 mismatch를 Error로 잡는다.
- 런타임과 에디터 판정이 다르다.

권장:

- Runtime에 `DialogueTagRegistry` 또는 `DialogueTagDefinition`을 만들고 parser/validator가 같은 정의를 참조한다.
- effect close 시 stack top 이름 검증을 parser에도 추가한다.

### `FacingDirection`이 슬롯과 바라보는 방향을 동시에 표현한다

파일:

- `HDialogue/Runtime/Portrait/FacingDirection.cs`
- `HDialogue/Runtime/Portrait/SlotConfig.cs`
- `HDialogue/Runtime/Graph/Nodes/DialogueLineNode.cs`

`FacingDirection.Left/Right`는 캐릭터가 바라보는 방향을 뜻하는 동시에 `SlotConfig.Slot`의 화면 배치 슬롯으로도 쓰인다. 지금은 단순하지만 의미가 섞여 있다.

권장:

- `StageSlot` 또는 `PortraitSlot` enum을 별도로 둔다.

### `DialogueCatalogValidator`가 fallback/range/switch 검증을 아직 하지 않는다

파일: `HDialogue/Editor/Validator/DialogueCatalogValidator.cs`

choice key sync는 개선됐지만 다음은 아직 없다.

## 보안 및 안정성

- 선택지 조건 우회 가능성이 가장 크다. `OnChoicePresent`가 유효 선택지를 넘겨도 `SelectChoice()`가 검증하지 않으면 외부 입력 경계가 아니다.
- Cancellation은 전반적으로 사용하지만, `PlayCatalog()` 재호출과 `Stop()`의 종료 이벤트 계약이 다르다.
- `UniTaskVoid` 사용은 Unity 이벤트/MonoBehaviour에서 허용될 수 있으나, 예외 로깅 정책이 없다. `OperationCanceledException` 외 예외가 발생할 때 관측 방식이 불명확하다.
- `AudioManagerBlipAdapter` null guard는 좋지만, token prewarm/존재 검증은 아직 없다.
- `DialogueTextController`에서 `Sfx` 토큰은 여전히 no-op이다. 기능 스펙에 포함된 태그라면 미구현을 명확히 UI/validator에서 알려야 한다.

## 구조적 결함

- `DialogueDirector`의 node processor 책임이 한 클래스에 집중되어 있다.
- 태그 정의가 parser/validator로 분산되어 있다.
- 포트레이트 위치 제어가 `SetSlot`, `_ApplyPoseImmediate`, `_ShakeAsync`, `_BounceAsync`에서 모두 `RectTransform.anchoredPosition`을 직접 만진다. base position과 transient motion offset이 분리되지 않았다.
- runtime asmdef가 `HCUP.HUI`, `HCUP.HAudio`, `HCUP.HCore`, `HCUP.HUtil`을 모두 참조한다. 현재 코드 기준 실제 필요성이 낮은 참조가 섞였을 가능성이 있다. 어셈블리 의존성은 기능 단위로 더 줄이는 것이 맞다.
- `DialogueDirectorState.Finished` 주석은 "ExitNode 도달 또는 Stop() 호출"이라고 되어 있지만 실제 `Stop()`은 `Idle`로 전이한다. 문서와 구현이 어긋난다.

## 완성도 평가

현재 완성도: 68%

근거:

- 그래프 실행, 텍스트 출력, 포트레이트 연동, 선택지 필터링, 기본 validator는 존재한다.
- 직전 리뷰에서 지적된 일부 핵심 사항은 반영됐다.
- 하지만 선택 실행 검증, 종료 계약 일관성, 포트레이트 motion 안정성, 태그 정의 단일화, validator 확장, 필수 참조 정책이 아직 닫히지 않았다.
- 테스트가 보이지 않는다. 최소한 parser/validator/director choice branch에 대한 EditMode 테스트가 필요하다.

## 개선 우선순위

1. `DialogueDirector.SelectChoice()`에 현재 valid key 검증을 추가한다.
2. `PlayCatalog()` 재호출 시 기존 카탈로그 종료 이벤트/정리 계약을 `Stop()`과 일관되게 만든다.
3. `CharacterPortraitController` Motion 취소 시 `anchoredPosition` 복구를 보장하거나 base position/motion offset을 분리한다.
4. `DialogueTagRegistry`를 도입해 parser/validator의 커스텀 태그 정의를 단일화한다.
5. `DialogueCatalogValidator`에 fallback, IntRange, Switch, branch edge 검증을 추가한다.
6. 필수 SerializeField에 Assert 정책을 적용한다.
